# The Oracle Runbook - OCI Cloud Labs

> Hands-on Oracle Cloud Infrastructure labs covering **Oracle AI Database 26ai**, OCI networking, Compute provisioning, operating-system validation, and secure-access concepts.

This repository started with an Oracle AI Database 26ai Autonomous AI Database lab and now also records the OCI infrastructure foundation used for subsequent hands-on exercises.

The goal is to keep each activity reproducible, technically focused, and independent of any employer or customer environment.

## Oracle AI Database 26ai lab

The database lab uses an Autonomous AI Database Serverless instance with the Transaction Processing workload.

The workflow validates the database from SQL, creates relational objects, performs DDL and DML, and explores the native `VECTOR` datatype.

The vectors are intentionally small manually defined three-dimensional values. They are used to make vector storage and distance calculation easy to understand and are **not embeddings generated by an AI model**.

### Vector validation result

Reference vector:

```text
[1,0,0]
```

## OCI infrastructure sequence

### Networking

The OCI network foundation contains:

```text
OCI-LAB-VCN           10.10.0.0/16
├── Public subnet     10.10.10.0/24
│   └── 0.0.0.0/0 -> OCI-LAB-IGW
└── Private subnet    10.10.20.0/24
```

The private subnet is retained as part of the architecture even though the free-tenancy service limits observed during the lab did not permit NAT Gateway or Service Gateway creation.

### Compute

`OCI-LAB-VM01` was provisioned with Oracle Linux Server 9.8 using the Always Free eligible `VM.Standard.E2.1.Micro` shape.

The lab validates:

- provisioning work request
- image and shape
- primary VNIC
- public/private addressing
- boot volume
- Instance Metadata Service v2
- serial-console access through OCI Cloud Shell

### SSH and OS user authentication

The SSH lab preserves the default key-based `opc` access while adding a separate local user with a user-specific OpenSSH `Match User` rule.

This demonstrates how authentication behavior can be scoped to one operating-system account rather than changing the global SSH policy.

## Lab rules

- These are personal disposable learning environments, not production sizing guides.
- No customer or employer system names, addresses, tickets, screenshots, or internal architecture are used.
- No passwords, private keys, wallet files, connection secrets, or credentials are stored here.
- Ephemeral public IP addresses are intentionally omitted.
- Production implementations should apply network, IAM, operating-system, encryption, monitoring, and access controls appropriate to the workload.
